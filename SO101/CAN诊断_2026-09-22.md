# 航凯 TG9801 / 若比特 CAN 实机诊断

> 这是 2026-09-22 的历史诊断。第二天（9-23）夹爪改走 RS485 就通了，CAN 这条路已放弃。
> 夹爪现在怎么接、怎么用见 [数据采集](数据采集.md) 第 2.5 节。

本轮目标是把未确认项实际查清，不发送夹爪初始化、抓放、位置、模式或 EEPROM 指令。
SO101 和 AR5 没有参与本轮测试。

## 已确认

| 项目 | 证据和结论 |
|---|---|
| 电脑到适配器的通信 | `/dev/ttyUSB0`、115200、8N1，配置查询稳定返回通过校验的帧 |
| 封装后三字节 | 通道、帧格式、帧类型；`00 01 00` = 通道0 / 扩展 / 数据；`00 00 00` = 标准数据 |
| 适配器原 CAN 位速率 | 读取 `0x01FFFED0` 的低4字节 `40 42 0f 00` = **1000000 bit/s** |
| UART 位速率 | 读取 `0x01FFFE90` 的低4字节 `00 c2 01 00` = **115200 bit/s** |
| 标准帧硬件过滤器 | filter 0：值 `0x80000000`，掩码0；已启用，全ID接收 |
| 扩展帧硬件过滤器 | filter 1：值 `0xc0000000`，掩码0；已启用，全ID接收 |
| 接收软件过滤 | 新诊断脚本保留所有通道、ID、帧格式、帧类型及原始字节，没有要求回复必须为ID1 |
| 自动重发 / 自动总线管理 | 均读回0；不把这解释成 CAN 物理总线已经正常 |

字段定义依据 [python-can 项目自己的 Robotell 驱动源码](https://python-can.readthedocs.io/en/main/_modules/can/interfaces/robotell.html)
中的 `_writemessage`、`_readconfig`、`set_hw_filter`；适配器配置回复是本次现场实际读取的，
不是仅对照另一款适配器的文档。配置通道为 `FF`，读取使用扩展远程帧，写入使用扩展数据帧。

## 完成的夹爪查询

读取指令来自 TG9801 手册第4.6节：`03 00 00 01 01 00 00 00` 查询位置/状态，
`07 01 00` 查询目标力。

| 测试范围 | 查询次数 | 结果 |
|---|---:|---|
| 原1 Mbps，ID1和2，标准/扩展格式，两种读取指令，每次等250ms | 8 | 无原始接收字节 |
| 原1 Mbps，发送ID **0..2047**，标准/扩展格式，读位置，每次等20ms | 4096 | 无原始接收字节 |
| 1M / 800k / 500k / 400k / 250k / 125k / 100k / 50k，发送ID **0..15**，标准/扩展，两种读取指令，每次等30ms | 512 | 无原始接收字节 |

速率扫描只更改适配器 CAN 位速率。每次设置后都重新读取确认，最后恢复到原 **1 Mbps**，
再次读回 `40 42 0f 00` 确认成功。没有改变夹爪参数、适配器 UART 速率、硬件过滤器或接线。

扫描并未覆盖所有“速率 × ID”的组合，也未遍历完整29位扩展ID空间。
配置应答证明适配器串口协议有效，**不等于已经测到 CAN 线上存在正确波形或对端 ACK**。
发送报文无应用层回复，也不能单独证明设备不支持 CAN。

## 仍需要硬件侧证据

1. 这根 CAN 线上适配器能否与已知正常的设备双向通信：断电换接原因时手，仅读取角度作对照。
2. 夹爪接线端实际供电、共地、终端匹配及总线波形/ACK：需要万用表、CAN分析仪或示波器。
3. 这只夹爪实物的接口版本、当前协议和设备地址：厂家上位机成功读回、出厂配置记录或厂家确认。

手册4.2有“CAN（通过适配盒）”，4.1又给出CAN_H/L线色。此前据此直接断定
“若比特不能用、必须换航凯盒”的结论证据不足，已撤回。
同样，旧文档“若比特不支持配置、CAN速率固定”的说法已被本次实际读写结果否定。

## 文件与复现

诊断入口：`atom_robot/ar5/probe_hkvr_can.py`，在 SO101 目录下用 dexgraspvla 环境跑。

```bash
cd ~/yuhang_workspace/算法/DexGraspVLA-/SO101
# 默认不修改适配器配置，读取配置并测试ID1/2的标准和扩展查询
D=diagnostics/hkvr_can_$(date +%Y%m%d); mkdir -p "$D"
PYTHONPATH= ~/miniforge3/envs/dexgraspvla/bin/python -m atom_robot.ar5.probe_hkvr_can \
    --port /dev/serial/by-id/usb-1a86_USB_Serial-if00-port0 --out "$D/hkvr-can-probe.json"
```

- `--port` 默认是 `/dev/ttyUSB0`。本机同时插着 CH340 和 Prolific，`ttyUSBn` 会互换，所以显式给 CH340 的 by-id 路径（和 `config.py` 里 `HandConfig.port` 同一个口，
  现在是灵巧手的备用 CAN）。跑之前先 `fuser -v /dev/serial/by-id/usb-1a86_USB_Serial-if00-port0` 查有没有别的程序占着。
- `--out` 默认写到 `/tmp/hkvr-can-probe.json`，不会自己留档；要留档就像上面那样写进本目录的 `diagnostics/`。

显式 `--bitrates` 才临时改适配器速率，脚本在 finally 中恢复并读取确认原值。
恢复逻辑已用模拟串口验证正常退出和发送异常两种情况；设备拔出或进程被强杀时，
软件无法保证恢复，重新插入后应先读取实际速率。
