# 规划器测试：看参考图，在场景里框出没有名字的物体

2026-10-17 的测试记录。10-28 补测了本地的 Xiaomi-Lens-0（按文字框物体并直接出掩码），见文末「补测」。

**目的**：上游的规划器只能用文字指定目标（"抓红色杯子"），我们要的是给一张物体照片：pick up the【物体图片】。物体往往没有通用的名字，所以要测模型能不能看着参考图，在头部相机画面里把同一个东西框出来。框出来以后，后面的 SAM → Cutie → 控制器都不用改，因为控制器只吃掩码。

**结论**：**采用 qwen3-vl-plus**（百炼接口）。一次请求同时发参考图和场景图，直接要框，测试 17 次全中。我们账号能调的千问开源模型都做不到可靠：一次请求的做法 18 次只中 1 次；最好的两步法也只有 4/6。

> [!IMPORTANT]
> 只测了**一个案例**（一个目标、一个场景），每种配置 3~6 次。外观相近的干扰物、目标不在场景里这两类难案例还没测，qwen3-vl-plus 也没经过这类考验。见文末「还没测」。

## 采用的方案：qwen3-vl-plus

| 项目 | 值 |
|---|---|
| 接口 | 百炼 OpenAI 兼容接口，`https://dashscope.aliyuncs.com/compatible-mode/v1`（北京地域） |
| 模型 | `qwen3-vl-plus`（闭源托管，参数量没公布，推测是 Qwen3-VL-235B-A22B） |
| 输入 | 一次请求：参考图在前、场景图在后，加上任务说明；要不要加外形说明都行，这个案例里没区别 |
| 输出坐标 | 相对坐标，宽、高都归一化到 0~999，换成像素：`x = v / 999 × 图宽`、`y = v / 999 × 图高` |
| 思考模式 | 关（这个模型默认就是关的） |
| 速度 | 每次 2.5~3.0 秒 |
| 价格 | 输入 1 元、输出 10 元每百万 token（32K 以内）；每次约 680 + 70 个 token，**约 0.15 分钱**；北京地域每个模型送 100 万 token |
| 密钥 | 环境变量 `DASHSCOPE_API_KEY`，**不要写进 `inference_utils/config.yaml`**（仓库是公开的） |

还没接进上游规划器，要改的地方见 [`../待测试.md`](../待测试.md) 的 C6。

`测试集/案例01/`（不进 git）：

## 结果

### 1. 一次请求，同时发参考图和场景图（`ref_grounding_min.py`）

| 模型 | 参考在前 | 场景在前 | 每次耗时 |
|---|---|---|---|
| **qwen3-vl-plus** | **11/11**（只给图片 6 次、加外形说明 5 次），交并比 0.82~0.90 | 没测，不需要 | 2.5~3.0 秒 |
| qwen3.5-397b-a17b | 0/3 | 1/3 | 2.0~2.4 秒 |
| qwen3.5-122b-a10b | 0/3 | 0/3 | 1.5~1.8 秒 |
| qwen3.6-35b-a3b | 0/3 | 0/3 | 1.0~1.2 秒 |
| qwen3.7-flash（商用，对照） | 0/3 | — | 1.4~1.9 秒 |

开源模型 21 次的描述**全都认对了**（"灰色六角柱，中间有白圈的孔"），也没有一次框到别的物体上，但框落在目标旁边的空白处：3.6 和 3.7 偏左约 90 像素，397b 偏下约一个物体高，122b 散乱。所有框画在一张图上：`结果/汇总_案例01_各模型框.png`。

qwen3-vl-plus 加不加外形说明，结果几乎一样（5 次全中 vs 5 次全中），这个案例分不出外形说明的作用：场景里灰色六角形的东西只有一个。

### 2. 坐标探针：一次框 6 个已知物体（`coord_probe.py`）

6 个物体的平均交并比：

| 模型 | 只发场景图（要求 0~999） | 只发场景图（不指定坐标约定） | 两张图，参考在前 | 两张图，场景在前 |
|---|---|---|---|---|
| qwen3-vl-plus | 0.91 | 0.92 | 0.88 | 0.90 |
| qwen3.5-397b-a17b | 0.91 | 0.88 | 0.73 | 0.82 |
| qwen3.5-122b-a10b | 0.91 | **0.94** | 0.43 | 0.29 |
| qwen3.6-35b-a3b | 0.85 | 0.78 | 0.16 | 0.14 |

**Qwen3.5/3.6 只发一张图时框得准**，等效宽高都在 640×480 左右，坐标约定没错。**一次请求里只要有两张图，坐标就整体偏**，换顺序也没用，越小的模型偏得越厉害。qwen3-vl-plus 不受影响，这就是第 1 节只有它命中的原因。没查清是百炼服务端处理多图的方式造成的，还是模型本身的问题（本机部署没测）。

### 3. 两步法：坐标只从单图拿（`two_step.py`）

第一步只发场景图，让模型框出台面上所有物体；第二步把候选编号画在场景图上，和参考图一起发，只问"是几号"。

| 模型 | 命中 | 第一步把目标框进候选 | 第二步选对（目标在候选里时） | 每轮耗时 |
|---|---|---|---|---|
| **qwen3-vl-plus** | **6/6** | 6/6 | 6/6 | 约 10 秒 |
| qwen3.6-35b-a3b | 4/6 | 10/12 | **4/4** | 约 2.3 秒 |
| qwen3.5-122b-a10b | 4/6 | 8/12 | 4/5 | 约 5 秒 |
| qwen3.5-397b-a17b | 1/6 | 12/12 | 1/6：**5 次选了白色六角件** | 约 6.5 秒 |

"第一步把目标框进候选"一栏把作废那一批的第一步也算进去了，所以是 12 次（见「踩过的坑」第 6 条）。

开源模型在两步法里有两个短板：
- **第一步会漏掉小物体**：目标只有 29×45 像素。
- **认物会认错**：397b 认定白色六角件是"深色六角柱、白色圆孔"，和参考图对上了。这是真正的看错，不是坐标问题。

qwen3.6-35b-a3b 只要目标进了候选，第二步就全选对了；它的失败全在第一步。

外形说明在第二步可能有一点帮助（目标在候选里时，只给图片 3/7，加外形说明 6/8），但样本太少，不算结论。

## 为什么选 qwen3-vl-plus

- 一次请求、两步法都全中，一共 17/17。
- 一次请求就够，2.7 秒左右；开源模型要用两步法，最好的 qwen3.6-35b-a3b 只有 4/6。
- 价格上不吃亏：每次约 0.15 分钱，比 qwen3.6-35b-a3b（约 0.2 分）还便宜。开源模型在百炼上没有价格优势，它们的好处只有更快，以及以后能本地部署。
- 按官方评测，开源的 qwen3.6-27b、qwen3.5-397b、qwen3.6-35b-a3b 定位分数都比 Qwen3-VL-235B 高（RefCOCO 92.5 / 92.3 / 92.0 对 91.1）。但那测的是"按文字框物体"，不是"按参考图找物体"，和这里的实测结果对不上。

## 用法

都在仓库根目录跑，先 `export DASHSCOPE_API_KEY=sk-xxxx`。只依赖标准库和 PIL，`dexgraspvla` 环境就能跑，不用装 `openai`。

```bash
PY="env PYTHONPATH= $HOME/miniforge3/envs/dexgraspvla/bin/python"
C=规划器测试/测试集/案例01

# 主测试：默认 qwen3-vl-plus、只给图片、参考在前
$PY 规划器测试/ref_grounding_min.py $C
$PY 规划器测试/ref_grounding_min.py $C --input 图片加外形
$PY 规划器测试/ref_grounding_min.py $C --model qwen3.6-35b-a3b --order 场景在前

# 坐标探针：四种问法
$PY 规划器测试/coord_probe.py $C --models qwen3-vl-plus qwen3.6-35b-a3b
# 改了解析规则后，用已存的回复离线重算，不调接口
$PY 规划器测试/coord_probe.py $C --reanalyze 规划器测试/结果/探针_20261017_142700

# 两步法
$PY 规划器测试/two_step.py $C --model qwen3.6-35b-a3b --input 图片加外形

# 看账号能调哪些模型
$PY 规划器测试/ref_grounding_min.py --list-models

# 把已有结果画成图（不调接口）：每个方案一张，上面是实际发出的提示词，下面四栏是四个模型实际框出来的结果
$PY 规划器测试/plot_results.py      # → 结果/可视化/方案一_一次请求.png、方案二_两步法.png
```

| 选项 | 说明 |
|---|---|
| `--input` | `图片` / `图片加外形` / `文字`（只给外形说明、不给参考图的对照组，还没跑过） |
| `--order` | `参考在前`（默认）/ `场景在前` |
| `--coords` | `auto`（模型名带 qwen3 就按 0~999 相对坐标，否则按像素）/ `relative` / `pixel` |
| `--thinking` | `off`（默认，统一关）/ `on` / `unset`（不发这个参数，给非千问模型用） |
| `--dry-run` | 只拼请求、画真值框，不调接口 |

每次运行的请求（图片用文件名代替）、原始回复、可视化图都存在 `结果/` 下（不进 git）。主测试结果目录名是 `案例名_输入_时间`。如果某个配置的坐标约定配错了，结果里按另一种约定换算后能对上真值，脚本会给出提示。

## 踩过的坑

1. **Qwen2.5-VL 已在百炼下线**：上游 README 和论文用的 `qwen2.5-vl-72b-instruct` 返回 `403 access_denied`，不是账号问题。百炼价格页写着"Qwen2.5 系列等已下线模型不再可用"。
2. **坐标约定不一样**：Qwen2.5-VL 给的是缩放后图像的像素坐标；Qwen3-VL 和 Qwen3.5~3.8 给的是**相对坐标，归一化到 [0, 999]**（百炼文档原话）。按像素理解会全错，而且多数数值落在 640×480 以内，越界检查发现不了。
3. **思考模式默认值不一样**：qwen3.5~3.8 默认开，qwen3-vl-plus 默认关。开源版开思考时只能流式调用，非流式会报错。比较时统一关掉。
4. **Qwen3.5/3.6 一次请求发两张图，坐标就乱**：见第 2 节。要用它们框物体，坐标只能从单图请求里拿。
5. **`--list-models` 不能按名字筛 `vl`**：`qwen3.8-max`、`qwen3.7-plus` 这些能看图的模型名字里没有 vl。
6. **Qwen3.5/3.6 不按要求写编号**：要它们给 `id`，它们常写进 `label`（"prism: small gray …"），或者干脆不写；6 个物体可能都叫 `physical object`。坐标探针第一次因此判成"框出 0/6"，两步法第一次因此把 6 个候选并成 1 个、编号图上画的是名字。现在探针认 `label`，两步法按列表顺序自己编号。作废的两步法结果在 `结果/作废_两步法编号bug_1017/`。
7. **上游 `preprocess_img` 的裁剪是按上游相机写死的**：只留画面上方 60%、横向 40%~90%，其余涂白，用在 335 上会涂掉大半张桌子。测试一律用整图。
8. **接口地址**：控制台给的地址可能带业务空间编号（`…cn-beijing.maas.aliyuncs.com/compatible-mode/v1`），照抄给 `--base-url`。国际账号用 `dashscope-intl.aliyuncs.com`。本机直连百炼是通的，脚本不走 `.bashrc` 里的代理。

## 还没测

- **难案例**：两个外观相近的灰色六角件（比如一长一短）；目标不在场景里（看它会不会照样框一个）；参考图换成手机拍的。要现场摆、用 335 拍。
- **只给文字的对照组**（`--input 文字`）：看参考图本身起多大作用。
- **开思考**：可能改善 397b 认错物体的问题，代价是慢很多；开源版要先给脚本加流式调用。
- **开源模型的改进路线**（以后想本地化时）：qwen3.6-35b-a3b 的短板只在两步法第一步漏框，可以把第一步换成 SAM 自动分割来出候选。另外本机部署时多图坐标会不会也乱，没测。

## 补测（10-28）：Xiaomi-Lens-0，本地按文字框物体、直接出掩码

**目的**：看能不能用一个本地模型同时给出目标的框和掩码，替代「规划器给框 → SAM 分割第一帧」这两步；或者在数据转换时自动标第一帧的框（现在是人工标，有一部分是目测的）。只测了黑色套筒，按文字描述找，不是按参考图找。

**结论**：
- **描述写全时认得出**：训练数据 50 条的第一帧全中，腕部画面 8/8，现场俯视图也中。
- **措辞影响很大**：只写 `black sleeve` 会认错 5/50；`白板上的黑色套筒` 把整块白板分了出来（抓了「白板」这个名词）。换一种物体都要先试描述。
- **被夹爪挡住大半时基本认不出**（最好 2/10），而且**每次都会框一个别的东西，不会说找不到**。不能拿它在遮挡后重新找目标，抓取过程还是靠 Cutie 跟踪。
- **每张 0.77 秒，显存峰值 9.0 GB**：只适合开局用一次或离线标框，不能逐帧用。和控制器、Cutie 放在同一张 16 GB 卡上放不放得下，没测。

| 项目 | 值 |
|---|---|
| 模型 | 小米 SeerRay 实验室 2026-10-16 发布，底座 Qwen3.5-4B，约 50 亿参数，Apache 2.0。技术报告 arXiv 2610.23279，权重 `SeerRay-Lab/Xiaomi-Lens-0`（Hugging Face） |
| 做法 | 语言模型生成 `<\|mask\|>`，一个轻量解码器把它和视觉编码器的图块特征结合，解出掩码；不另挂分割模型 |
| 本机位置 | 代码和权重在 `~/xxr/Xiaomi-Lens-0`（不在工作区，权重 8.7 GB）；conda 环境 `lens0`（torch 2.10.0+cu128、transformers 5.4.0，没装 flash-attn） |
| 提示词 | 官方格式：`Locate all instances in the image that match the description "…". Report bbox coordinates and masks.` |
| 输出 | 框（0~1000 相对坐标）+ 掩码；掩码在模型输入画布的分辨率上，要缩回原图大小 |
| 速度、显存 | 每张 0.77 秒（生成 + 第二遍前向解掩码）；加载后 8.6 GB，峰值 9.0 GB |

### 结果

对照是训练数据里现有的掩码（SAM + Cutie）。第一帧按交并比 ≥ 0.7 算中；被遮挡时套筒只露一点，按交并比 > 0.3 算中。腕部和现场图没有对照掩码，是看图判断的。

| 测试 | `black sleeve` | `黑色套筒` | `the black cylindrical sleeve on the white board` |
|---|---|---|---|
| 训练数据第一帧（头部，50 条） | 45/50 | 48/50 | **50/50** |
| 合爪前 0.5 秒，夹爪挡住大半（头部，10 条） | 0/10 | 2/10 | 2/10 |
| 腕部，合爪前 1 秒（8 条） | 8/8 | 没测 | 没测 |
| 现场俯视图（10-28，套筒立在白板中间） | 错：框到右下角的黑色物体 | 中 | 中 |

- 第一帧认对的那些：交并比中位 0.89，中心和现有掩码差约 2 像素，面积相近（约 1450 对 1500 像素）。
- 只写 `black sleeve` 认错的 5 条：第 25、26 条框了整块白板，第 27、28、32 条框了画面边上的红色或黑色物体。
- 被遮挡时框到的是画面上方的红盒子、马克笔这些东西，10 条每条都只输出一个实例。
- 现场图另试了 `白板上的黑色套筒`：分出来的是整块白板。

### 踩过的坑

1. **官方 `infer.py` 写死了 FlashAttention-2**，5070 Ti 上没装。调 `load_model_and_processor(..., attn_implementation="sdpa")` 就能跑；视觉部分和线性注意力层会提示退回普通实现，不影响结果。
2. **训练数据里的图像是 BGR**（见主 README「数据格式」），喂给它之前要转成 RGB。
3. **它总会输出至少一个实例**，看不到目标时也一样，要靠别的办法判断「没找到」。

### 还没测

- 盒子、香蕉、水瓶、长盒子、充电器（训练数据在移动硬盘上）。
- 同款干扰物（比如两个一样的瓶子），以及目标不在画面里的情况。
- 接到 Cutie 前面（第一帧用它的掩码，往后让 Cutie 跟踪），和现在的 SAM 掩码比跟踪效果。
- 部署时和控制器、Cutie 同卡的显存。
